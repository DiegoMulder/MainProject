# Matching builds, aimed drops, two-way doors and multiple enemies

## First: share a matching game build

A build is a frozen copy of the game. Editing the Unity project does not update an EXE you built yesterday. Moving a prefab together with its .meta file preserves its identity; adding a new network prefab or changing its network scripts still requires everyone to update.

The NetworkConfig mismatch was reproduced by connecting the old **Builds/MansionFeedbackRound/SurvivalFP.exe** to the current editor. That build predates the Walkie Talkie entry added to the shared registry. The registry now contains 11 game prefabs, including the radio. Netcode correctly refuses the incompatible client. The previous player network behaviour layout also predates PlayerRadio. Keeping the old EXE while replacing just a prefab in the editor cannot fix that client.

1. Exit Play mode.
2. Choose **Tools > Survival FP > Build Current Multiplayer Game**.
3. Wait for Unity to finish successfully.
4. Open the project folder in Explorer, then **Builds/Current**.
5. Send the **whole Current folder** to each friend, for example as a ZIP. They should extract it before starting SurvivalFP.exe. The EXE needs its Data folder and DLLs beside it.
6. Everyone should run that same copy. When testing an editor host, rebuild after changing networking content.
7. Start at MainMenu, host a lobby, share its join code, wait for the other player, choose difficulty, then start.

Use Current as the usual build location. MansionFeedback, MansionFeedbackRound and SettingsRadio are older snapshots, not the current release. They are retained so existing files are not silently deleted. **Do not mix them with Current.**

NetworkCompatibility.txt beside the new EXE lists its build time, prefab identities and network behaviour order. Compare this file between computers if unsure. The editor build check stops a build if the game registry contains nulls, duplicate identities, development prefabs, or omits a game network prefab. It also checks that network scene management and matching-prefab validation remain enabled. It cannot magically update a friend's older copy.

This update uses **Protocol Version 1** because doors now send an extra network value. Older SettingsRadio builds use version 0 and must also be replaced. When you change the order or layout of NetworkBehaviours/NetworkVariables in future code changes, increment Protocol Version on the session prefab and rebuild every client. Matching prefab identities alone do not describe the complete network message layout.

The session prefab is **Game/Prefabs/Game Management/Multiplayer Session**. It references **Game/Data/NetworkPrefabs.asset** once. MainMenu creates the persistent session; Game does not need its own NetworkManager. Do not add a second manager or transport to a room, player or scene. Add a new network prefab once to the shared list, then rebuild for everyone. The autogenerated DefaultNetworkPrefabs list is not the session's gameplay list.

## Change how items drop

Q drops the selected item along the direction of the camera, including up and down. Its initial movement uses that direction too. The server decides the safe placement for multiplayer; clients see the replicated result.

1. Open **Game/Prefabs/Player/Network Survivor** in Prefab Mode.
2. Select the root and find **Player Inventory**.
3. Expand **Dropping**.
4. Change one value, save, and test standing and crouching near a wall.

| Setting | What it does | Default |
| --- | --- | --- |
| Drop Forward Distance | Preferred distance from the camera, in metres | 0.9 |
| Drop Forward Impulse | Initial speed along the camera direction | 2.3 |
| Drop Minimum Clearance | Extra space from the player or detected obstacle | 0.04 |
| Drop Check Padding | Extra safety around the item's collider bounds | 0.015 |
| Drop Vertical Correction Limit | Maximum upward adjustment when the ideal point is blocked | 0.45 |

The solver tries the aimed point first. A nearby wall shortens the distance. If the point overlaps the player or floor, the solver tries small upward steps and moves just beyond the player's body. It checks the entire path from the camera as well as the final point. It never searches behind your back. If there is no safe placement, you keep the item; step away and try again.

The check uses a sphere enclosing the item's original collider bounds. Large or long objects need more room than small ones. Keep pickup colliders close to the actual model; an oversized invisible collider makes placement unnecessarily restrictive. The physics body and impact sound/noise components still work after release. A downward drop can immediately strike the ground, which is expected.

For the offline course, change the same settings on **AI-Tools-DEV/Prefabs/SurvivalPlayer** separately. It is a different player prefab.

## Ordinary doors open away from you

The server looks at which side of the closed door you stand on and sends both the opening angle and open state to everyone. Closing returns to the original closed rotation regardless of opening side. The exit keeps its separately validated opening direction.

When making a normal door variant:

1. Duplicate **Game/Prefabs/Doors/Ordinary Door**.
2. Keep the root's local blue Z axis perpendicular to the closed doorway. This is the door's front/back direction.
3. Keep the hinge at the left edge, with the leaf extending along local positive X from the hinge. For the supplied prefab, hinge X is -1.1 and panel centre X is +1.1 relative to it.
4. The supplied panel is 2.2 metres wide inside a 2.4 metre opening. The small side gaps let its thickness clear the frame in either direction.
5. Keep a BoxCollider on the leaf, sized to its model. Leave the closed hinge rotation at its authored closed pose.
6. Set Open Angle to the desired maximum swing, normally 100 degrees. Speed controls animation speed.
7. Leave space on both sides of the door for the entire swing. Avoid placing cabinets or walls inside that arc.
8. Register the new network prefab once and assign it to MansionSettings if it replaces ordinary generated doors.

Positive opening rotation swings this +X leaf toward local -Z. A player standing on local +Z therefore gets a positive swing; the opposite side gets a negative swing. Because the calculation uses the door's local space, rotating a room or door by 90 degrees does not break it. If you build a right-hand hinge or reverse the leaf axes, adapt the sign calculation in DoorInteractable.OpeningAngle too.

The mansion planner reserves the ordinary door's full swing in both directions when choosing furniture, so generated tables do not block the doorway. If you place furniture manually, keep the same space free.

Before an ordinary door opens, it checks its BoxCollider through the proposed arc. It stays closed when the swing is obstructed, instead of selecting a direction toward the opener or moving through furniture. This opening check does not continuously solve collisions against moving actors after the animation starts; avoid intentionally walking into a moving leaf. Closing is the existing animated return to the closed pose.

## Choose how many monsters each difficulty spawns

1. In the Project window select **Game/Data/Difficulty.asset**.
2. Expand **Profiles**, then the difficulty you want.
3. Change **Enemy Count**. The supplied values are Easy 1, Medium 1, Hard 1 and Extreme 2.
4. For example, set Extreme to 3 to get three monsters next round.
5. Save. Host a lobby, choose Extreme and start a new round.

Zero deliberately creates a round with no enemies, useful for exploring new rooms. There is no special name check: a profile called Custom works too. Room count and objective count remain editable alongside enemy count.

The server copies the selected profile when a round begins. Editing the asset during an existing round does not add or remove live monsters. Return to the lobby and start a fresh round to apply it. If no Difficulty Config is assigned, MansionSettings has a fallback Enemy Count.

All monsters use **Game/Prefabs/Enemy/Mansion Stalker**. Register that prefab only once, regardless of how many instances spawn. Change its speed, perception and memory settings to affect every instance; make separate prefab variants only if you actually need different monster types and extend the spawner accordingly.

The generator builds navigation first. It chooses reachable room navigation points at least eight metres from players and at least three metres from each other, preferring distant rooms. If the requested count cannot fit, generation reports a clear failure instead of stacking monsters or placing them outside the navigation mesh. Add more connected rooms or reduce the count. Very large counts also cost more CPU; the Inspector minimum does not promise unlimited practical capacity.

Each monster has its own target, memory, search timers and random sequence. A noise is delivered to every monster, and each checks its own distance and hearing multiplier. A loud radio can attract several monsters; a quiet nearby impact might attract only one. Hearing does not consume the event. Closets and downed-player rules remain per monster.

The player's heartbeat uses the nearest spawned monster. It does not create extra heartbeat tracks for extra monsters. Returning to the lobby despawns all monsters and removes their hearing/closet listeners. Starting again uses the newly selected count.

## A useful manual check after your own changes

Use two computers or an editor plus a fresh standalone build. Join by Relay code. Confirm both names and difficulty, then start. Check the same rooms, pickups, monsters and door direction on both screens. Drop while standing, crouching, aiming up/down and beside walls, furniture and stairs. Listen for impact sounds. Let two monsters hear a noise, hide, and test downing with a teammate present. End the round, return both players to the lobby and start again. Neither player should need to reconnect.

Automated validation helpers and their reports belong in **AI-Tools-DEV**, not game prefabs or scenes. They only run when explicitly invoked for development. Real microphone quality still needs people speaking into microphones; simulated radio noise is not a listening test.
